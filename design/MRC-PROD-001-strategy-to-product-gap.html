0 · The verdict

Moracat has over-built the ecosystem and under-built the loop

This audit covers 56 web pages, 39 API controllers and 120 data models. Three parallel code audits did the reading, and I re-checked every critical claim against the source by hand. Fact The platform is technically deep:

  • Append-only clinical records with consent tiers.
  • A capability-based vet portal with invite-only clinic onboarding.
  • A lifecycle engine, a feeding engine and household pricing.

Roughly 50 of the 120 models are schema-only: warehouse, drivers, loyalty, gift cards, referrals, badges, shipments.

The strategy's moat is one loop: a clinic writes to a Cat ID → the owner sees it and acts → the owner returns to that clinic → more cats get written. Every link in that loop is broken or missing today.

The next 90 days are not about new surfaces. They are about closing one loop and making it measurable.

Infrastructure findings that change priorities

  • The scheduler is unreliable. The API runs on Render's free plan (Frankfurt), which sleeps when idle; cron runs in-process on a single instance with no lock and no missed-run alert. Renewals, lapses and vaccination reminders can silently not happen.
  • Data residency. The database (Neon), API and storage are all in the EU, clinical records included. There is no documented PDPL transfer basis.
  • Resilience is on paper only. Neon point-in-time restore has never been tested; Sentry only runs if a DSN is set; there is no uptime monitor; web unit tests don't run in CI.
  • Security posture. Tokens live in localStorage; staff 2FA is optional; rate limiting is in-memory; Turnstile was rolled back.

7 · Customer journeys

Where each journey breaks today

Legend: solid = works · amber = partial · dashed red = missing.

A · New cat owner (kitten)

Content / clinic / ad→Home: name the cat→Register→Cat ID ceremony→Profile (no chip, food, source)→Kitten first-year plan & schedule→First box (gated; Tamara only)→Delivery tracking→Clinic connection (claim / home clinic)→Reminders (no clinic named)→Graduation at ~9 months

Friction: after the ceremony, the owner lands on a dashboard with nothing time-sensitive to do. No vaccination schedule exists for a kitten with no recorded vaccines, so the product is silent during the highest-need weeks. Missing: the life-stage schedule, a "find a clinic near you" step (directory by district), and kitten plan entry.

B · Existing cat owner

Landing→Register cat→Build health profile (vaccines only; key fields not editable)→Import history (photo of vaccine card → document)→Recommendation (feeding engine, not tied to food they already use)→Purchase (gated)→Vet ecosystem (directory + consent, no visible clinic records)

Friction: experienced owners already have a food brand and a vet. They need "keep my brand coming" (Refill, year 2) and "my vet's records, in one place" (health page + clinic claim). Quick win: let the owner upload a photo of the paper vaccine card as a document and enter the next due date. That feeds reminders without pretending the upload is verified.

C · Multi-cat owner

Account→Add several cats→Individual profiles→Different diets (engine per cat; not in the box)→Different replenishment schedules→Consolidated checkout (household pricing, gated)→Co-owners / carers in the household

Friction: adding cat #2 goes through the full creation wizard again, with no "add another" shortcut that copies the household city and district. Decision: keep one household delivery cadence (monthly). Per-cat schedules are a do-not-build: they multiply shipping cost on thin margins (FIN-002 shared-box logic).

D · Veterinary clinic

Invite→Registration wizard→Review & verify→Sandbox test scan→Go live→Search Cat ID (walk-ins not found)→Create patient + claim SMS→Record visit & entries→Update health (no attachments UI)→Recommend care (in-app summary only)→Owner returns (reminder naming clinic)→Clinic sees "patients returned"

Friction: onboarding is excellent, and then the clinic's first real patient isn't in the system. This is the single highest-leverage break in the whole product.

18 · Prioritisation

Four buckets

Build now · days 1–30

  1. Reliability floor: every reminder and renewal depends on a scheduler that currently sleeps.
  2. Event log + attribution + CVAC: every later decision needs it, and CVAC is the north star.
  3. Owner health page + per-cat privacy page + health field inputs: makes existing vet data visible, fixes two 404 links and the allergy wipe.
  4. Clinic-created patient + SMS claim + duplicate merge: the break that stops the network from forming.
  5. Reminders that name and route to the clinic (+ preferences respected): the clinic's reason to use Moracat.
  6. Scannable QR → public cat page: the Safety job becomes real, and it acquires new owners.

Build next · days 31–90

  1. Recurring payments (Moyasar token, opt-in auto-renew, dunning) — after the founder decision
  2. Subscription self-service completion
  3. Vaccination certificate PDF + verify
  4. Clinic Today dashboard (/vet/org/summary)

  6. Kitten-year path (schedule, graduation)
  7. Household co-owners + ownership transfer
  8. WhatsApp channel + quiet hours
  9. Vet attachment upload (presigned)

Build later · scale, data or partner dependent

  • Breeder / shelter batch issuance (needs 10+ willing breeders)

Feature: T1 · Reliability floor

As the Moracat team, I want every scheduled job to run on time or alert us, so that no vaccination reminder or renewal notice is ever silently missed.

Acceptance criteria

  1. The API runs on an always-on Render instance; /health is monitored every minute with an alert on failure.
  2. Each lifecycle job takes a Postgres advisory lock, so two instances can never double-run it.
  3. Each job pings a heartbeat on success; a missed run alerts within 2 hours.
  4. Sentry DSNs are set in web and API; a test error appears in Sentry.
  5. A Neon point-in-time restore is performed into a branch, documented in DEPLOY.md.

Backend

  • withJobLock(name, fn) wrapper using pg_try_advisory_lock; heartbeat URL per job from env; render.yaml plan change.

Frontend

  • None.

★ · The one system

If the website disappeared: rebuild the Living Cat Record

The system: one record per cat that clinics write, owners hold, and reminders turn into return visits. It is the product version of MRC-STRAT-001's north star, and everything else (the box, community, homepage) is a surface on top of it.

What it contains

  1. Identity core: Cat ID number, photo, sex, birth date, district, microchip, household members with roles, and a URL QR token.
  2. Two write paths into one record: clinic entries (append-only, consent-tiered, the existing engine) and owner entries (marked self-reported). Includes the clinic-created patient with an SMS claim link, so walk-ins enter the record on day one.
  3. The owner view: a timeline, vaccination status, weight chart, conditions and allergies, a privacy page with the access log, and a verifiable certificate.
  4. The rules engine (packages/core): life stage, vaccination schedule, weight watch. Deterministic and vet-approved.
  5. The return loop: a reliable scheduler sends reminders that name the clinic, by SMS/WhatsApp/email, and link to that clinic. The clinic sees "patients returned".
  6. The measurement spine: a first-party event log computing CVAC, claim rate, district density and reminder → return.

How people use it

  • Reception scans or types a Cat ID. If the cat isn't found: "New patient" → name + owner mobile → the vet records the vaccine.
  • The owner gets an SMS naming the clinic, taps, registers in under two minutes, sees the ceremony, and finds the vaccine already on Luna's record with the next dose date.
  • Weeks later a reminder says "Luna's booster is due at Al-Olaya Vet" → one tap to WhatsApp the clinic. The clinic writes again, and CVAC ticks up.
  • A boarder scans the certificate QR and sees "vaccinations verified". A finder scans the collar and messages the owner without seeing their number.

Why this creates leverage

  • It uses what's already built. The append-only clinical engine, consent tiers, invite-only clinic onboarding and lifecycle reminders are the hard parts, and they exist. Roughly 60% of this system is wiring and surfaces, not new engines.
  • It creates the only asset time protects. A competitor can copy a box in a quarter; it cannot backfill years of clinic-written history.
  • It acquires owners for free. Every clinic visit becomes a claim link, fixing the strategy's biggest sensitivity (acquisition volume) without paid media.
  • It gives the box a reason to exist. The record knows the cat's age, weight and stage, so the plan is computed from the cat, as the Design Authority's 2026-07-10 amendment requires. The commerce engine switches on as a feature of the record, not a separate store.
  • It is honest infrastructure. Portable, consent-first and non-exclusive, so clinics, regulators and eventually breeders can adopt it without fearing it.

Ninety days, in order: make it reliable and measurable (week 1–2) → make the record visible (week 2–4) → let clinics create patients and send owners home with an ID (week 3–5) → route reminders back (week 4) → make it verifiable (week 6–7) → turn the kitten year into a schedule (week 9–12).
